HOW IT WORKS · AN ILLUSTRATIVE RUN

A test failed. Here’s how the run handled it.

One prompt: rename user_id to account_id across seven repos. Along the way a test failed, the repo went back with the findings, and the coordinator made one call the spec didn’t cover, then logged it for you to confirm. Here is every step, straight from the event log.

This run is illustrative: its timings and events are mocked, but every event type is one OpenFleet really logs. To replay a real run yourself, try pnpm demo.

01 · THE WHOLE RUNOne conversation, then hands-off

OpenFleet writes every step of a run to events.jsonl: who did what, to which repo, and when. The coordinator is the agent you talk to. For the first forty seconds it grills you: it asks every question it needs answered, then writes a spec. Once you approve the spec, you are done talking. It creates a git worktree for each repo and hands each one to three short-lived sub-agents in turn: a planner, an implementer and a tester.

Press replay to watch all 203 events land. Six repos start within ten seconds of each other. mobile sits idle until sdk-js is done, because the spec ordered it that way.

02 · STATEEvery repo walks the same path

The coordinator moves each repo through the same phases: pending, planning, plan-review (it checks the plan against the spec before any code is written), implementing, testing, post-test (it checks the test results before calling the repo done), and done. Almost always forwards: the one exception is sdk-python, which goes back from testing to implementing (the ↺) with the tester’s findings attached. mobile spends most of the run in pending, waiting on sdk-js.

03 · MESSAGESThe coordinator talks, agents report back

Sub-agents never talk to each other. Each one gets a single instruction from the coordinator, does its job in that repo’s git worktree, and ends with a structured openfleet-report: a status, a summary and, if it has one, a question. Twenty-three instructions out, twenty-three reports back, plus the spec handoff with you at the start.

04 · THE CODE314 lines across 24 files

Most of the diff is renames and tests. The api adds a migration and a contract test; the SDKs note the breaking change in their changelogs. sdk-python’s second implementer adds the deprecated alias and one test for it.

05 · THE DECISIONSFive moments the coordinator stepped in

Most of a run is agents working alone. These five moments are where the coordinator stepped in: pinning a contract, answering a question, sending a repo back after a failed test, making a call the spec didn’t cover, and holding an ordering. Watch step 4: the coordinator decided something on its own, and wrote it down for you to confirm before anything merges.

06 · VERIFY177 tests, one retry

Each tester runs the repo’s own test command. Contract tests, in blue, check every consuming repo against the same rows in account.json. Press run to replay them: sdk-python fails one test, gets a fresh implementer, and passes on the retry.

07 · WHAT’S LEFTNothing merges without you

The run ends in draft PR mode, as agreed in the grill. The coordinator commits each worktree to its openfleet/account-id branch, pushes it and opens a draft PR. Every PR links to the other six and carries the run summary, which lists the one assumption for you to confirm. Nothing merges until you do.

Want to look before anything leaves your machine? Choose staged in the grill instead, and the changes wait uncommitted in each worktree.

Run it on your own repos

$npm create @openfleet-tools@latest
