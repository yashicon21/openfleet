01 · THE WHOLE RUNThree minutes, eight lanes

OpenFleet writes every step of a run to events.jsonl: who did what, to which repo, and when. The coordinator is the agent you talk to. It spends the first minute with you, settling questions and writing a spec. After you approve, it splits the work into one child per repo and hands each child to three short-lived sub-agents in turn: a planner, an implementer and a tester.

Press replay to watch all 63 events land. The api and web lanes run side by side, a few seconds apart, because the coordinator spawns agents one at a time and then lets them work in parallel.

02 · STATEEvery child walks the same path

The coordinator moves the project, and each child, through a fixed set of phases. The run only ever goes forward. There is no retry arrow in this replay because no child needed one: every plan validated first time and every test run passed.

The slow phases are the ones where a model is thinking. Planning includes the coordinator reading both plans and settling an open question, which is why it outlasts the planners themselves.

03 · MESSAGESThe coordinator talks, agents report back

Sub-agents never talk to each other. Each one gets a single instruction from the coordinator, does its job in the child’s git worktree, and ends with a structured openfleet-report block: a status, a one-line summary and, if it has one, a question. Six instructions out, six reports back, plus the spec handoff with you at the start.

05 · THE ONE DECISIONWhere should the fixtures live?

Both repos test against the same contract: greeting.schema.json and five example rows in greeting.example.json. Those files live in the OpenFleet project, outside either repo. The api planner spotted the trap and asked about it; the web planner had quietly planned to copy them.

The coordinator answered with one line in the api implementer’s instructions: Decision: copy contract fixtures into test/fixtures/. Step through what that avoided.
